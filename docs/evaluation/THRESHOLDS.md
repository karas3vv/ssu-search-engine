# Порог сходства и запросы без ответа

Без порога Qdrant возвращает ближайшие статьи даже для вопроса, на который в корпусе нет ответа. Параметр `--min-score` позволяет не показывать результаты с низким косинусным сходством. Это оценка близости векторов, а не вероятность правильного ответа. По умолчанию порог выключен; выбранного рабочего значения пока нет.

По новому отчёту на 2665 статьях получен [предварительный кандидат `0.33`](BENCHMARK.md#dev-на-полном-корпусе): на dev он сохраняет Hit@5 = 35/36 и MRR@5 = 0.9167, убирая все четыре отрицательные выдачи. Это расчёт по сохранённым числам без новых запросов к модели. Ручная проверка разметки и новый holdout ещё не завершены; автоматически этот порог не включается.

## Получить отчёт с оценками

В прежнем `data/evaluation/benchmark-dev.csv` сохранены id статей и время, но нет оценок сходства. Он по-прежнему читается для просмотра, ручной проверки и продолжения без порога. Числа сходства восстановить из id нельзя.

Новый оценщик сохраняет `retrieved_scores` в том же порядке, что и `retrieved_article_ids`, а также использованный `min_score`. Для полного подбора нужен свежий запуск без `--min-score` и без продолжения старого отчёта:

```bash
python -m habr_search.evaluation.evaluate --queries evaluation/benchmark_dev.csv \
  --qdrant-url http://127.0.0.1:6333 --timeout 300 \
  --output data/evaluation/benchmark-dev-scored.csv
```

Это 40 обращений к MWS. Если предстоит расширение индекса до всего корпуса, лучше получить этот отчёт уже после расширения. Прерванный новый отчёт можно продолжить через `--resume`, указав другой свободный `--output`. Если в продолженном отчёте остались старые строки без оценок, для подбора он не подходит. Разные версии индекса и разные пороги смешивать нельзя.

## Сравнить пороги без API

```bash
python -m habr_search.evaluation.calibrate --queries evaluation/benchmark_dev.csv \
  --report data/evaluation/benchmark-dev-scored.csv \
  --output data/evaluation/thresholds-dev.csv
```

Команда читает только два файла. Она сравнивает исходную выдачу и 201 порог от −1 до 1 с шагом 0.01. Для каждого значения считает Hit@k, MRR@k на положительных запросах и число пустых выдач на `no_answer`. При одинаковом улучшении выбирается самый мягкий порог. Если улучшить отказы без снижения исходных Hit и MRR не удалось, порог не предлагается. Настройки поиска не меняются.

Сохраняются только первые `top_k` результатов исходной выдачи. Фильтрация убирает слабые результаты, не меняя порядок остальных. Она не оценивает другие варианты ранжирования и не восстанавливает уже отсечённые результаты. Поэтому отчёт, полученный с `--min-score`, не принимается для подбора. Время работы с новым порогом надо измерять отдельным запуском; прежнее время в расчёт не переносится.

## Проверить выбранное значение

Предложение предварительное: dev содержит лишь четыре искусственных отрицательных вопроса, а исходные метки релевантности ещё требуют [ручной проверки](BENCHMARK.md#ручная-проверка). После расширения корпуса проверьте отрицательные примеры заново. Доработайте dev-разметку и зафиксируйте порог до финального запуска нового holdout. Не выбирайте значение по результатам holdout.

Один и тот же `--min-score` поддерживают команды `habr_search.retrieval.search`, `habr_search.evaluation.evaluate` и `habr_search.web.app`. Добавляйте его только с проверенным числом. В веб-приложении порог задаётся при запуске сервера; для пользователя дополнительных переключателей нет. При отсутствии подходящих результатов страница покажет пустую выдачу. Перенос настроек на другой корпус или модель требует повторной проверки.

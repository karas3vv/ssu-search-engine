# Порог сходства и запросы без ответа

Qdrant возвращает ближайшие статьи даже для запроса без подходящего ответа. Косинусное сходство не является вероятностью релевантности. Основной поиск теперь использует BGE-M3; порог по умолчанию выключен. Пороги от другой модели без повторной проверки переносить нельзя.

## Результат проверки BGE-M3

Проверен только dev-отчёт `results-20261024-093959-849385.csv`: 2665 статей, 36 положительных и 4 искусственных отрицательных запроса. Holdout для выбора порога не использовался. До фильтрации Hit@5 — 30/36, MRR@5 — 0,7546; все четыре отрицательных запроса имели непустую выдачу.

| Порог | Hit@5 | MRR@5 | Пустых отрицательных | Пустых положительных |
|---|---|---|---|---|
| выключен | 30/36 | 0,7546 | 0/4 | 0/36 |
| 0.508 | 30/36 | 0,7546 | 1/4 | 0/36 |
| 0.51 | 29/36 | 0,7269 | 1/4 | 1/36 |
| 0.56 | 28/36 | 0,7176 | 3/4 | 1/36 |
| 0.57 | 28/36 | 0,7176 | 4/4 | 3/36 |

Порог 0.57 скрывает все четыре отрицательные выдачи, но теряет два ранее найденных полезных ответа: перефразировку про список Joomla и вариант названия Nuitka. Пустых положительных выдач три, поскольку один из этих запросов и раньше не находил ожидаемую статью в top-5. Число пустых выдач и число потерянных попаданий — разные показатели.

Мелкая сетка обнаружила кандидат 0.508: он скрывает один отрицательный запрос, сохраняя текущие Hit и MRR. Однако у ложного первого результата оценка 0.5073422, а самый слабый найденный ожидаемый ответ имеет 0.5080922. Разрыв около 0.00075 слишком мал, чтобы по четырём примерам считать правило устойчивым. Кандидат **не включён автоматически**. При небольших изменениях данных, ответов модели или разметки результат может измениться.

## Сравнение без API

Если исходный dev-отчёт уже сохранён, повторно вызывать модель не нужно:

```bash
python -m habr_search.evaluation.calibrate \
  --queries evaluation/benchmark_dev.csv \
  --report data/evaluation/results-20261024-093959-849385.csv \
  --step 0.001 \
  --output data/evaluation/thresholds-bge-m3-new.csv \
  --details-output data/evaluation/thresholds-bge-m3-new-queries.csv
```

Сравниваются пороги от −1 до 1. По умолчанию шаг 0.01; `--step` принимает значения от 0.0001 до 1. Мелкий шаг позволяет увидеть узкие интервалы, но сам по себе не повышает надёжность отбора.

CSV содержит Hit@k, MRR@k, число пустых отрицательных и положительных выдач, число потерянных попаданий, версию коллекции и шаг. Необязательный `--details-output` сохраняет исходную и отфильтрованную выдачу каждого запроса для предварительно выбранного порога. При одинаковом улучшении выбирается более мягкий порог; без сохранения исходных Hit и MRR предложение не выдаётся. Старое время запроса не переносится в новый эксперимент. Файлы и настройки приложения не перезаписываются.

Подходят только полные отчёты обычного `evaluate`, содержащие `retrieved_scores` и полученные без `--min-score`. Из id статей или RRF-оценок гибрида косинусное сходство восстановить нельзя. Если отчёта ещё нет, его можно получить отдельно:

```bash
python -m habr_search.evaluation.evaluate \
  --queries evaluation/benchmark_dev.csv \
  --qdrant-url http://127.0.0.1:6333 --timeout 300 \
  --output data/evaluation/bge-m3-dev-scored.csv
```

Эта последняя команда обращается к MWS по одному разу на запрос; сама калибровка модель и Qdrant не вызывает.

## Явное применение

`--min-score` поддерживают `retrieval.search`, `evaluation.evaluate` и `web.app`. Порог задаётся при запуске сервера, а не отдельным пользовательским переключателем на странице. Он фильтрует карточки; если ни одна не проходит, интерфейс показывает, что подходящих статей не найдено.

Например, **для эксперимента**, а не как подтверждённая настройка:

```bash
./run.sh --min-score 0.508
```

Обычный `./run.sh` продолжает работать без порога. Не применяйте это значение к Tantivy или RRF гибрида.

## Что ещё требуется

Нужны более разнообразные вручную проверенные отрицательные запросы: не только вымышленные названия технологий, но и вопросы по отсутствующим темам, неоднозначные запросы и близкие к тематике корпуса вопросы без полного ответа. После выбора правила на dev нужна отдельная проверка на свежем наборе. Уже просмотренный holdout не следует многократно использовать для подбора нового значения. Без такой проверки нельзя обещать, что один числовой порог решает задачу отказа без потерь.

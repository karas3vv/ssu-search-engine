# Триграммы и исправление опечаток

`habr_search/retrieval/spelling.py` содержит алгоритм и чтение словаря, `habr_search/retrieval/spellcheck.py` — команды его построения и проверки. Модуль работает перед семантическим поиском. Векторы статей не пересчитываются.

## Словарь

```bash
python -m habr_search.retrieval.spellcheck build --qdrant-url http://127.0.0.1:6333
```

Команда читает заголовки и тексты уже проиндексированных фрагментов. Частота слова равна числу разных статей с этим словом: повтор заголовка и перекрытие фрагментов не увеличивают её. Регистр и `ё/е` объединяются при сопоставлении; исходный текст запроса сохраняется.

Словарь записывается в `data/spelling.sqlite3`, исключённый из Git. Он содержит слова, частоты, имя коллекции, число статей и точек, версию формата, время создания и SHA-256 частот. Триграммы строятся в памяти при загрузке. Новых зависимостей нет. MWS, SQLite-корпус и векторы для построения не используются; Qdrant читается без изменений.

Существующий файл не перезаписывается. Для нового индекса создайте другой словарь:

```bash
python -m habr_search.retrieval.spellcheck build --qdrant-url http://127.0.0.1:6333 \
  --dictionary data/spelling-next.sqlite3
```

Поиск проверяет совпадение имени коллекции и числа точек. Замена содержимого с сохранением количества точек этой проверкой не обнаруживается: после любого изменения текстов словарь нужно пересобрать. При построении также нельзя обновлять индекс; изменение числа точек обнаруживается, изменение содержимого с тем же числом — нет.

## Алгоритм

1. Для неизвестного слова подбираются кандидаты с общими символьными триграммами. Границы `^` и `$` учитывают начало и конец слова.
2. Проверяется расстояние OSA: вставка, удаление, замена и перестановка соседних букв. Это ограниченный вариант расстояния с перестановками: повторное редактирование одной подстроки не допускается.
3. Кандидаты упорядочиваются по числу правок, частоте по статьям, сходству триграмм и алфавиту.
4. Для применения допускается только единственный ближайший кандидат с одной правкой и частотой от трёх статей. Кандидаты на таком же расстоянии учитываются независимо от их частоты.

Общие принципы подбора через k-граммы и проверки расстояния описаны в [учебнике Introduction to Information Retrieval](https://nlp.stanford.edu/IR-book/html/htmledition/k-gram-indexes-for-spelling-correction-1.html). Пороговые значения и правила защиты здесь выбраны как начальная конфигурация и не доказывают улучшения качества поиска.

Исправляются слова длиной от 5 до 40 букв. Для длинных слов от 8 букв также показываются варианты с двумя правками, но они не применяются. Слова, встретившиеся хотя бы в одной статье, считаются известными. Редкие слова сохраняются в словаре, однако кандидатом становится только слово из двух или более статей.

Короткие слова, аббревиатуры целиком в верхнем регистре, смешанные алфавиты и внутренние заглавные буквы пропускаются. Не исправляются выделенные обратными кавычками слова и части адресов, путей или идентификаторов с цифрами и разделителями. Заглавное слово внутри фразы можно предложить проверить, но нельзя автоматически заменить: например, «репозитории Ктора» не превращаются в «репозитории Стора».

Это отдельная проверка слов, без понимания контекста. Ошибки, образующие другое известное слово, не исправляются. Опечатки самого корпуса могут попасть в словарь. Подбор по общим триграммам не гарантирует нахождение всех слов с двумя правками. Неизвестное название в нижнем регистре всё ещё может получить неверное исправление; для просмотра используйте режим `suggest`.

## Проверка без модели

```bash
python -m habr_search.retrieval.spellcheck suggest --query "автоматизаця документов"
```

Печатаются исходная фраза, предложенная фраза и кандидаты с числом правок и частотой. На текущих 500 статьях построен словарь из 81 088 слов. Проверены примеры `автоматизаця` → `автоматизация`, `автмоатизация` → `автоматизация`, `слвоам` → `словам`. «серверо» остаётся без замены, потому что подходит несколько слов. Это проверки поведения, а не статистическая оценка исправлений.

## Подключение к поиску

По умолчанию поиск работает с исходным запросом, как раньше. Показать предложения и искать исходную фразу:

```bash
python -m habr_search.retrieval.search --query "автоматизаця документов" \
  --qdrant-url http://127.0.0.1:6333 --spelling-mode suggest
```

Применить однозначные исправления и явно напечатать использованный запрос:

```bash
python -m habr_search.retrieval.search --query "автоматизаця документов" \
  --qdrant-url http://127.0.0.1:6333 --spelling-mode apply
```

Другой словарь указывается через `--spelling-db data/spelling-next.sqlite3`. Поиск делает одно обращение к MWS для выбранного запроса: исходного в режимах `off`/`suggest` или исправленного в режиме `apply`. Две выдачи не смешиваются.

## Сравнение качества

Подготовить исправленную копию dev-запросов без MWS:

```bash
python -m habr_search.retrieval.spellcheck prepare-evaluation --queries evaluation/queries_dev.csv \
  --output data/evaluation/queries-dev-corrected.csv
```

Сохраняются id, категории и ожидаемые статьи. Меняется только текст запроса. Исходная разметка остаётся на месте; совпавшие после исправления запросы отклоняются до записи. Существующий выходной файл не перезаписывается. На текущем dev-наборе изменяются два запроса: `coockie` → `cookie` и `ярксть` → `яркость`. Для неоднозначных или защищённых слов сохраняется исходная фраза.

Пользователь запускает получение выдачи для новой копии:

```bash
python -m habr_search.evaluation.evaluate --queries data/evaluation/queries-dev-corrected.csv \
  --qdrant-url http://127.0.0.1:6333 --timeout 300 \
  --output data/evaluation/dev-semantic-corrected-500.csv
```

Последняя команда обращается к MWS. Сравнивайте её отчёт с `dev-semantic-500.csv` по одинаковым `query_id`, ожидаемым статьям, коллекции, числу точек и `top_k`. Разный хеш запросов ожидаем, так как тексты изменены. Старый отчёт нельзя передавать через `--resume`: это другой запуск. Исходный dev-результат уже равен максимуму, поэтому здесь прежде всего проверяются возможные ухудшения; для оценки пользы потребуется более сложный dev-набор.

Отложенный набор после первого измерения не используем для подбора правил. Словарь, правила и запросы нужно зафиксировать перед новой независимой проверкой.

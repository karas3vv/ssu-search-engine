# Проверка на 80 запросах

Исторические сравнения на 500 и 2665 статьях ниже относятся к Gemma, поддержка которой удалена. Они сохранены как результаты экспериментов; актуальные замеры BGE-M3 и гибрида приведены в [инструкции гибрида](../HYBRID.md), порог BGE-M3 — в [проверке порогов](THRESHOLDS.md).

Набор составлен по первым 500 подготовленным статьям исходного корпуса. Все 24 целевые статьи входят в этот срез; те же запросы подходят для проверки после расширения индекса. Это предварительная разметка по текстам, а не законченная оценка качества. Dev проверен на 500 и 2665 статьях; полная ручная проверка найденных статей и новый holdout ещё не выполнены.

| Файл в `evaluation/` | Запросов | Целевых статей | Назначение |
|---|---:|---:|---|
| `benchmark_dev.csv` | 40 | 12 | настройка и разбор ошибок |
| `benchmark_holdout.csv` | 40 | 12 | проверка после фиксации настроек |

В каждом наборе 36 запросов с ответом и 4 отрицательных. Положительные запросы включают прямые формулировки, перефразировки, опечатки и варианты названий. На статью приходится три формулировки. Статьи и тексты запросов между наборами не пересекаются.

Dev использует темы старых `queries_dev.csv` и `queries_holdout.csv`: их результаты уже просматривались, поэтому старый holdout не считается новым независимым экзаменом. Новый holdout использует 12 других статей: дроны, MongoDB, музыкальные лады, бинарная сериализация, LensDB, IRC/XMPP, TrueType VM, утилиты Windows, SSD, ввод спецсимволов, логические схемы и локальный запуск моделей. Формулировки не выбирались по успешной выдаче модели. Не меняйте настройки по результатам нового holdout.

`benchmark_articles.csv` содержит ссылки, темы, основания меток и SHA-256 подготовленных текстов. `benchmark_manifest.json` фиксирует состав набора, отпечаток исходного среза и статус `seed_labels_need_review`. Флаг `retrieval_results_reviewed` остаётся `false`: найденные результаты ещё не проверены человеком. Эталонная статья не обязательно единственная полезная; другие результаты нужно оценить отдельно.

Единственный пропуск — `benchmark_dev_max_webhooks_typo`: «Где находится текст сообщния в вебхуках MAX и как устроены inline-кнопки?». Статья `1005282` была четвёртой на 500 статьях и вышла из первой пятёрки после расширения корпуса. Теперь найдены `1047336`, `1053638`, `1060696`, `1090738`, `1048882`. Среди них есть материалы про MAX, клавиатуры и структуру сообщений, но общая тема ещё не означает полный ответ на обе части вопроса. Проверять нужно содержание, сохраняя исходную метрику до утверждения новых меток.

Словарь того этапа локально предлагал «сообщния → сообщения». Это проверка предложения опечаточника, а не доказательство улучшения выдачи: исправленный запрос в MWS ещё не отправлялся. Ещё два эталона перешли с первого места на второе: перефразировки про Ktor-репозитории и HTTP-обработчик отправки писем. Поэтому падение MRR не сводится к одной опечатке.

По сохранённым оценкам бесплатно рассчитаны 201 порог и исходный вариант. Таблица — `data/evaluation/thresholds-dev-full.csv`:

| Порог | Hit@5 | MRR@5 | пустые отрицательные выдачи |
|---|---:|---:|---:|
| выключен | 35/36 | 0.9167 | 0/4 |
| 0.30 | 35/36 | 0.9167 | 3/4 |

`0.33` — самый мягкий порог на сетке 0.01, который убирает все четыре отрицательные выдачи без дополнительного снижения исходных Hit и MRR. Это предварительный кандидат по dev, а не подтверждённая настройка для всех запросов: отрицательных примеров всего четыре, они искусственные. Порог в приложении не включён. Более высокий порог уже может терять известные ответы.

Для ручной проверки подготовлен `data/evaluation/benchmark-dev-full-review.csv`: 201 строка, включая не найденную эталонную статью. `relevance` и `comment` оставлены пустыми; исходные CSV и manifest не менялись. Приоритет — пять строк нового пропуска и эталон, затем остальные результаты ниже первого места. После ручной проверки фиксируются разметка и настройки, и только затем запускается новый holdout. Подбор порогов, экспорт таблицы и проверка словаря не обращались к MWS и не изменяли индекс.

## Запросы без ответа

Пустой `relevant_article_ids` допустим только для категории `no_answer`:

```csv
query_id,category,query,relevant_article_ids
unknown,no_answer,Как настроить QuokkaFS-Z19?,
```

Все восемь отрицательных примеров используют вымышленные названия. Проверено отсутствие этих названий в заголовках и полных текстах всех 2665 статей. Это искусственные проверки, а не репрезентативная выборка настоящих пользовательских вопросов без ответа. Близкая по теме статья не отвечает на вопрос о вымышленной системе. При следующем расширении корпуса отрицательную разметку надо проверять заново.

Hit@k и MRR@k считаются только для положительных запросов. Для `no_answer` отдельно выводится число пустых и непустых выдач. По умолчанию поиск возвращает ближайшие статьи без порога сходства. Добавлен необязательный `--min-score`; порог в приложении не включён; исторический кандидат `0.33` не относится к BGE-M3. [Подбор по сохранённым оценкам](THRESHOLDS.md) следует повторять при изменении разметки, сохраняя полезные ответы, а затем проверять результат на holdout.

## Порядок запуска

Проверить только формат CSV без сети и создания отчётов:

```bash
python -m habr_search.evaluation.evaluate --queries evaluation/benchmark_dev.csv --dry-run
python -m habr_search.evaluation.evaluate --queries evaluation/benchmark_holdout.csv --dry-run
```

После запуска Qdrant оценить dev. Полный запуск с нуля делает 40 обращений к MWS:

```bash
python -m habr_search.evaluation.evaluate --queries evaluation/benchmark_dev.csv \
  --qdrant-url http://127.0.0.1:6333 --timeout 300 \
  --output data/evaluation/benchmark-dev.csv
```

Оценщик использует исходные запросы: подсказки не применяются автоматически. Каждый запрос векторизуется один раз. Индекс статей не изменяется. В новые отчёты записываются версия коллекции, время запроса, оценки сходства и использованный порог, в сводку — медиана и p95. Прежний отчёт из 15 столбцов читается, но для подбора порога ему не хватает оценок. Время не включает ввод ключа и загрузку токенизатора. Условную цену API программа не придумывает; число запросов известно до запуска.

При остановке используйте тот же набор, `--resume data/evaluation/benchmark-dev.csv` и новый свободный `--output`. Старые отчёты без столбцов `index_revision` и `elapsed_ms` не подходят для нового `--resume`; исходные CSV остаются на месте. Смешивать результаты разных версий индекса нельзя. Не изменяйте индекс во время оценки; ручные правки Qdrant должны сопровождаться обновлением `habr_index_revision`.

## Ручная проверка

Подготовить таблицу по завершённому отчёту, не обращаясь к MWS или Qdrant:

```bash
python -m habr_search.evaluation.review --queries evaluation/benchmark_dev.csv \
  --report data/evaluation/benchmark-dev.csv \
  --output data/evaluation/benchmark-dev-review.csv
```

Оцените найденные статьи по полному тексту, а не только по заголовку:

- `relevance = 0` — задача не решается;
- `relevance = 1` — полезная часть ответа, но задачи целиком не решает;
- `relevance = 2` — отвечает на запрос;
- `comment` — обоснование или замечание к формулировке запроса.

В таблицу включаются также эталонные статьи, отсутствующие в выдаче: для них `rank` пуст. `seed_relevant = yes` обозначает исходную метку, а не завершённую ручную оценку. Пустое поле метки другой статьи не означает нерелевантность. Для пустой выдачи сохраняется строка без статьи. Существующие таблицы не перезаписываются; экспорт не меняет исходную разметку.

После проверки дополните `relevant_article_ids` в dev всеми статьями, признанными подходящими, и сохраните новую версию CSV. Соответствующие старые отчёты больше не подходят для продолжения: хеш разметки изменился. Подсказки оценивайте отдельно — доля полезных предложений, ложных исправлений названий и влияние выбранного пользователем варианта на выдачу.

Финальный запуск для нового holdout выполняется той же командой с `evaluation/benchmark_holdout.csv` и отдельным путём отчёта, когда настройки уже зафиксированы. Он также требует 40 запросов к MWS. Его результаты следует честно публиковать без последующей настройки на этих же запросах.
